# 二维玩法取 osu!standard 的自由二维坐标，现有四轨谱面不适用于它

Status: accepted

二维玩法里 Note 用判定域上的**自由二维坐标**定位（参照 osu!standard）：没有轨道、没有列。命中判定沿用现有的"触点落在 Note 范围内"。因此仓库里**现有四张谱面在二维玩法里都无法表达**，二维曲目必须用 Thart 重新制。

## 为什么

- 参照对象是 osu! ——用户在 osu! 与**轨道式**的 Groove Coaster 之间选了 osu!。而 Groove Coaster 的官方机制是"只有一条轨道、判定点唯一（avatar 自己）"；若不取自由坐标，"按 osu" 就退化成一维列判定，与 Groove Coaster 的差别只剩画面风格。
- **制谱侧天然吻合**：Thart 录的就是 16:9 录入框内的**任意二维百分比**（`TouchToNoteConfig.FieldAspect = 16f/9f`、`fieldHeight = 6`），二维玩法只是把这个信息**保留到运行时**，而它今天被 `ThartChartBuilder.cs:469` 的最近簇聚列压成了列下标。
- **现有谱面本来就是列式的**，不是"自由坐标被导入器丢了"：`.osu` 转换源本身是 osu!mania 4K（1886 个打击物件 `y` 恒 384、`x` 仅 64/192/320/448 四值），Malody 同为 4K，`geometry-demo` 是 8 条路径且 `placement.y` 全为 0。它们能表达的"二维"只有列这一维。

## 后果

- `NoteData` 要加二维坐标字段并补 `ChartLoader` 校验（现在只校验 pathId/action/tick）。
- 二维玩法里 `SpatialDirector` 被二维映射取代；**三维玩法不动**，继续用列/路径式的现有谱面。
- 现有 4 张谱面（`Resources/Charts/*.json` 4 张 + `Charts/*.grchart` 3 个）**在二维玩法里作废**，只在三维玩法里继续可用。
- Note 的读时机不再能靠"从远处飞来"表达，需要 approach circle 一类的二维预告；具体数值与作者参数随判定域画幅一起定标。
- 命中半径、判定域坐标范围这些数值都要在二维玩法里重新定标（osu! 的 512×384 与 `r=(54.4−4.48·CS)·1.00041` 是它自己画幅下的产物，不能照搬）。

## 考虑过的替代

- **osu!mania 式多列**：能保留现有四张谱面，但"按 osu" 就没有内容了——那更接近本仓库已有的列式玩法，而不是 osu!。
- **两种都支持**：否。数据模型与制谱出口要同时服务两套坐标语义，而收益不清楚。
